# HiRoute repository invariants

- Keep this file and `.agents/skills/` as the canonical agent instructions. `CLAUDE.md` links here; `.claude/skills/` exposes only individually selected shared skills. Follow [agent instruction ownership](.agents/README.md) when changing these entry points. Read/edit shared skills through their canonical `.agents/skills/` paths so sibling references resolve consistently. Claude must not load Codex-only skills through indirect references; report the affected capability gap instead.
- Before writing to this repository's GitHub Issues, PRs or attachments, read and follow `rules` and `guidance.shared` in `issue-spec/config.yaml`.

- Read the [code map](docs/code-map/README.md) progressively: locate the relevant topic in the index or search `docs/code-map/` with `rg -n -i` using the user action, symptom or domain term. Once located, prefer reading the complete relevant code-map page, including its ownership boundaries and cross-references. Then follow the production owner and a representative scenario, expanding into linked code or guides as needed; unrelated map pages need not be loaded by default.
- Update affected map entries and local ownership guides when responsibilities, entry points or contract boundaries change. Keep entries searchable, concise and heuristic: where to look next, why it matters, and the key boundary. Detailed rules, parameter inventories, troubleshooting and validation history belong in their canonical spec, local guide or run record; the map is not a second specification.
- Use current issue-spec Design/answers, repository durable specs, code and executable tests as authority. Keep requirements self-contained. Optional personal history tools may explain earlier rationale; record applicable requirements in the current Issue/spec before implementation. Amend missing/conflicting requirements without blocking unrelated investigation.
- Stay within declared ownership. Only the convergence owner finalizes shared manifests, lockfiles and generated registries.
- For Desktop changes affecting layout, text wrapping, visual hierarchy or interactive form states, use [Desktop UI quality](.agents/skills/hiroute-ui-quality/SKILL.md). Verify the production style entry, affected viewport/state combinations and actual screenshots before handoff; select coverage by the changed behavior.
- For changes affecting persisted data, user configuration, recovery or published CLI/Gateway behavior, and at release handoff, use [compatibility maintenance](.agents/skills/hiroute-compatibility/SKILL.md). Resolve supported released sources and the existing conversion boundary; deliver necessary adaptation and affected regressions together. Unrelated edits do not require upgrade checks.
- Select checks by changed behavior and affected consumers: docs/tooling use their own checks; local implementation uses focused tests; product smoke is for affected business paths. Shared-library location alone does not require a full run. Cross-boundary contracts, dependencies or unresolved impact require expansion; keep explicit gates and unique assertions. Use `scripts/test-plan.py --base <comparison-ref>` and [test selection](docs/test-selection.md), recording any evidence-based scope adjustment.
- Select build/test locations using the caller's [HOME configuration](docs/validation-routing.md) and `scripts/validation.py`. Linux backend defaults local; Mac preserves its configured SSH Linux workbench. Validate an exact committed candidate locally, pushed candidate remotely. Backend checks exclude Desktop; macOS Desktop/Pilot runs on the configured Mac (local or SSH) with its existing shared-lock runner. Report Windows coverage from the checks actually executed. Hosted CI has its [own entry](docs/github-actions-validation.md). These are evidence limits, not product platform exclusions.
- Keep each checkout's default `target/`; share compiler objects only via sccache. Never use external Cargo targets or `cargo clean`. Use the documented local/remote cleanup tools after owners stop using artifacts; preserve unique evidence and never clean active runs.
- Development/test runtimes default to Debug; use the isolated Pilot default for product smoke and verify both roles’ applied levels. For failures, follow [diagnostic troubleshooting](docs/diagnostic-troubleshooting.md) before retrying; record the cause and evidence, not just process exit.
- Separate iterative diagnosis from final candidate validation. Default to Cargo fail-fast; classify observed failures and batch related fixes. An early stop leaves the failure set incomplete and unexecuted checks pending. For batch diagnosis, explicitly select `--no-fail-fast` within a declared scope; see [failure collection](docs/test-selection.md#failure-policy-and-completeness). Run only affected focused checks; do not relaunch the full short set after each intermediate edit or commit.
- Use the [validation feedback loop](docs/validation-feedback.md): pass a feature-specific `--plan`, `--phase focused/final` and explicit related run IDs. After a final failure, inspect the report and repair the applicable coverage, selection, build-context or harness gap; prove the regression catches the old failure. Isolated success alone does not establish environmental noise.
- Before feature handoff, assess the validation report's slowest three modules once: optimize, defer or insufficient evidence, with cost, smallest change and preserved assertions. Timing feedback is advisory; do not automatically refactor a frozen candidate or start another full run.
- After focused checks are green, freeze the candidate and complete its selected checks once; use the full short set only when its expansion criteria apply. Final success requires passing evidence for every selected check and explicit gate. Push for authorized validation or PR delivery only after the [public PR check](.agents/skills/hiroute-public-pr/SKILL.md) covers the complete outgoing history. Preserve unchanged-code evidence at its original SHA; docs/tooling-only follow-ups do not restart Rust validation.
- Bind evidence to the actual revision. Intermediate-revision evidence is diagnostic only; label reused evidence with its original revision and never present it as final evidence. After changes rerun affected checks and explicit gates. Run affected deterministic generators twice; the second run must produce zero diff. Unrelated edits do not require rerunning unaffected generators.
- Keep one current producer/ingestion contract per boundary. Register every legacy recovery reader, frozen fixture or catalog fallback in `contracts/compatibility-support.v1.json` with an owner, reason and removal condition; run `scripts/check-contract-convergence.py` after contract changes.
- Separate process exit from scenario `green`, `expected_red`, `red` and not-executed. Required missing/zero-selected cases fail; expected-red and fixture tests do not prove product completion. User-visible claims require the real production entry path.
- Treat 700 Rust lines as a soft responsibility-review threshold, not a hard cap: split only for a clear ownership boundary, never to reduce line count through low-value file splits or distorted logic. Split candidate-introduced files above 1100 lines; exact-base violations remain with their owning change.
